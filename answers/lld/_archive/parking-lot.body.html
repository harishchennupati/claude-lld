Stage 1 -- Clarify

The interviewer says one paragraph, and the five minutes after it are graded

The prompt

"Design a parking lot. It has multiple floors and different sizes of vehicle. Cars come in through entry gates and leave through exit gates; they get a ticket on the way in and pay on the way out. I want working code, not a diagram. Go."

1. The Vehicle -- start with what enters

Thinking: a car drives in, so start with the thing being parked. A plate and a type; Car, Motorcycle and Truck extend it so one can be special-cased later.
enum VehicleType { MOTORCYCLE, CAR, TRUCK }

abstract class Vehicle {                       // the first noun: what drives in
    final String plate;
    final VehicleType type;
    Vehicle(String plate, VehicleType type) { this.plate = plate; this.type = type; }
}
class Car        extends Vehicle { Car(String p)        { super(p, VehicleType.CAR); } }
class Motorcycle extends Vehicle { Motorcycle(String p) { super(p, VehicleType.MOTORCYCLE); } }
class Truck      extends Vehicle { Truck(String p)      { super(p, VehicleType.TRUCK); } }

2. The ParkingSpot -- where it goes

Thinking: a spot has a size and is either free or holding one vehicle. Keep it dumb: is it free, assign, release. Logic lives above it.
enum SpotType { SMALL, COMPACT, LARGE }        // a bigger spot fits smaller vehicles

class ParkingSpot {                            // where the vehicle goes
    final String id;
    final SpotType type;
    private Vehicle vehicle;                    // null == free
    ParkingSpot(String id, SpotType type) { this.id = id; this.type = type; }
    boolean isFree()          { return vehicle == null; }
    void    assign(Vehicle v) { this.vehicle = v; }
    void    release()         { this.vehicle = null; }
}

3. Fit rules -- which spot fits which vehicle

Thinking: a big spot can hold a small car, but hand out the smallest one that fits so trucks still find large spots. Per vehicle, the sizes it may use, smallest first.
// hand out the SMALLEST fitting spot first, so large spots stay free for trucks
final class Fit {
    static final Map<VehicleType, List<SpotType>> ORDER = Map.of(
        VehicleType.MOTORCYCLE, List.of(SpotType.SMALL, SpotType.COMPACT, SpotType.LARGE),
        VehicleType.CAR,        List.of(SpotType.COMPACT, SpotType.LARGE),
        VehicleType.TRUCK,      List.of(SpotType.LARGE));
}

4. The Ticket -- issued at entry

Thinking: which spot, which floor, which vehicle, when it came in; the exit time is stamped later. Remembering the floor makes unpark O(1). The id comes from an atomic counter -- the original used a bare static int, safe only because park holds a lock; say which you rely on.
enum TicketStatus { ISSUED, PAID, LOST, CLOSED }

class Ticket {                                 // issued at entry, priced at exit
    private static final AtomicInteger SEQ = new AtomicInteger();
    final int id;
    final ParkingSpot spot;
    final ParkingFloor floor;                  // remembered -> unpark is O(1)
    final Vehicle vehicle;
    final long entryMs;
    long exitMs;
    TicketStatus status = TicketStatus.ISSUED;
    Ticket(ParkingSpot spot, ParkingFloor floor, Vehicle vehicle) {
        this.id = SEQ.incrementAndGet(); this.spot = spot; this.floor = floor; this.vehicle = vehicle;
        this.entryMs = System.currentTimeMillis();
    }
}

5. Pricing -- the first "make it swappable"

Thinking: flat hourly by size, but they will ask for weekend surge. So the fee is not hard-coded; it sits behind an interface and is injected. A swappable algorithm behind an interface -- that is Strategy, and this is the moment it earned its name.
// "they'll want to change pricing" -> hide it behind an interface -> Strategy
interface PricingStrategy { double price(Ticket t); }

class FlatHourlyPricing implements PricingStrategy {
    private static final Map<SpotType, Integer> RATE =
        Map.of(SpotType.SMALL, 10, SpotType.COMPACT, 20, SpotType.LARGE, 40);
    public double price(Ticket t) {
        long ms = t.exitMs - t.entryMs;
        long hours = Math.max(1, (long) Math.ceil(ms / 3600000.0));   // bill >= 1 hr
        return hours * RATE.get(t.spot.type);
    }
}

6. Spot assignment -- Strategy again

Thinking: smallest-fit today, nearest-to-exit tomorrow. Same shape, same answer: hide the choice behind an interface so the lot never changes.
// "smallest fit today, nearest-to-exit tomorrow" -> same shape -> Strategy again
interface SpotAssignmentStrategy { ParkingSpot find(ParkingFloor floor, VehicleType type); }

class SmallestFitStrategy implements SpotAssignmentStrategy {
    public ParkingSpot find(ParkingFloor floor, VehicleType type) {
        for (SpotType st : Fit.ORDER.get(type)) {     // smallest fitting size first
            ParkingSpot s = floor.peekFree(st);
            if (s != null) return s;
        }
        return null;
    }
}

7. The Floor and the live board -- Observer emerges

Thinking: a floor holds spots, and finding a free one must not scan: a map from size to a deque of free spots gives O(1). The display board must update without parking logic knowing screens exist, so the floor just publishes "occupancy changed". A notifier decoupled from its listeners -- that is Observer. Note occupy: the assigned spot is the head that was just peeked, so it is a poll, not a linear remove -- the original used remove(s), which quietly made the O(1) claim false.
// "a board should update but not be wired into parking logic" -> publish/subscribe -> Observer
interface ParkingObserver { void onChange(String floorId, Map<SpotType, Integer> free); }

class DisplayBoard implements ParkingObserver {
    public void onChange(String floorId, Map<SpotType, Integer> free) {
        System.out.println("[board] " + floorId + " free=" + free);
    }
}

class ParkingFloor {
    final String id;
    private final Map<SpotType, Deque<ParkingSpot>> free = new EnumMap<>(SpotType.class);
    private final Map<String, ParkingSpot> all = new HashMap<>();
    private final List<ParkingObserver> observers = new ArrayList<>();

    ParkingFloor(String id) {
        this.id = id;
        for (SpotType st : SpotType.values()) free.put(st, new ArrayDeque<>());
    }
    void addObserver(ParkingObserver o) { observers.add(o); }
    void addSpot(ParkingSpot s)         { all.put(s.id, s); free.get(s.type).push(s); }
    boolean hasSpot(String id)          { return all.containsKey(id); }
    ParkingSpot peekFree(SpotType st)   { return free.get(st).peek(); }   // O(1)
    int freeCount(SpotType st)          { return free.get(st).size(); }   // O(1)

    void occupy(ParkingSpot s) {                 // O(1): the assigned spot is the head we just peeked
        Deque<ParkingSpot> q = free.get(s.type);
        if (q.peek() == s) q.poll(); else q.remove(s);
        notifyObservers();
    }
    void vacate(ParkingSpot s) { free.get(s.type).push(s);   notifyObservers(); }

    private void notifyObservers() {
        Map<SpotType, Integer> counts = new EnumMap<>(SpotType.class);
        for (SpotType st : SpotType.values()) counts.put(st, free.get(st).size());
        for (ParkingObserver o : observers) o.onChange(id, counts);
    }
}

8. The Lot ties it together -- the lock, and payment

Thinking: one lot owns floors, injected strategies and active tickets. Many gates call park at once, so find-and-occupy-and-assign is one critical section under one lock. Payment at exit is another swappable thing: Strategy a third time. The same plate parking twice is rejected before anything is touched -- the original silently overwrote the ticket.
interface PaymentProcessor { boolean pay(double amount); }              // Strategy #3
class CardPayment implements PaymentProcessor { public boolean pay(double a) { /* gateway */ return true; } }
class CashPayment implements PaymentProcessor { public boolean pay(double a) { return true; } }

class ParkingLot {                                   // one source of truth (Singleton)
    private static ParkingLot instance;
    private final List<ParkingFloor> floors = new ArrayList<>();
    private final Map<String, Ticket> active = new ConcurrentHashMap<>();
    private final ReentrantLock lock = new ReentrantLock();
    private PricingStrategy pricing;
    private SpotAssignmentStrategy assignment;

    private ParkingLot() {}
    static synchronized ParkingLot getInstance() {
        if (instance == null) instance = new ParkingLot();
        return instance;
    }
    void configure(PricingStrategy p, SpotAssignmentStrategy a) { pricing = p; assignment = a; }
    void addFloor(ParkingFloor f) { floors.add(f); }

    Ticket park(Vehicle v) {
        lock.lock();                                  // critical section: find + occupy + assign
        try {
            if (active.containsKey(v.plate)) throw new IllegalStateException("Already parked: " + v.plate);
            for (ParkingFloor floor : floors) {
                ParkingSpot spot = assignment.find(floor, v.type);
                if (spot != null) {
                    floor.occupy(spot);
                    spot.assign(v);
                    Ticket t = new Ticket(spot, floor, v);
                    active.put(v.plate, t);
                    return t;
                }
            }
            throw new IllegalStateException("Lot full for " + v.type);
        } finally { lock.unlock(); }
    }

    double unpark(String plate, PaymentProcessor payment) {
        lock.lock();
        try {
            Ticket t = active.remove(plate);
            if (t == null) throw new NoSuchElementException("No active ticket: " + plate);
            t.exitMs = System.currentTimeMillis();
            double fee = pricing.price(t);
            if (!payment.pay(fee)) throw new IllegalStateException("Payment failed");
            t.status = TicketStatus.CLOSED;
            t.spot.release();
            t.floor.vacate(t.spot);                   // O(1): ticket knew its floor
            return fee;
        } finally { lock.unlock(); }
    }
}

9. Prove it works -- including the race

Thinking: a main that parks, fills, rejects and unparks -- and then two gates racing for one compact spot on a thread pool. Exactly one must win; the assertion is what makes the lock a claim rather than a hope.
public class Main {
    public static void main(String[] args) throws Exception {
        ParkingLot lot = ParkingLot.getInstance();
        lot.configure(new FlatHourlyPricing(), new SmallestFitStrategy());

        ParkingFloor f1 = new ParkingFloor("F1");
        f1.addObserver(new DisplayBoard());
        f1.addSpot(new ParkingSpot("F1-S1", SpotType.SMALL));
        f1.addSpot(new ParkingSpot("F1-C1", SpotType.COMPACT));
        f1.addSpot(new ParkingSpot("F1-L1", SpotType.LARGE));
        lot.addFloor(f1);

        Ticket t = lot.park(new Car("KA01AB1234"));       // -> COMPACT
        System.out.println("parked at " + t.spot.id);
        lot.park(new Truck("KA02CD9999"));                // -> LARGE
        try { lot.park(new Car("KA03EF0001")); }          // compact+large gone, small can't fit
        catch (Exception e) { System.out.println("expected: " + e.getMessage()); }
        System.out.println("availability " + lot.availability() + " fullForCar=" + lot.isFullFor(VehicleType.CAR));
        double fee = lot.unpark("KA01AB1234", new CardPayment());
        System.out.println("fee for car: " + fee);        // 1 hr * 20 = 20

        // the race: two gates, one compact spot, exactly one must win
        ExitGate exit = new ExitGate(lot); EntryGate g1 = new EntryGate(lot), g2 = new EntryGate(lot);
        ExecutorService pool = Executors.newFixedThreadPool(2);
        Future<Ticket> a = pool.submit(() -> g1.admit(new Car("RACE-A")));
        Future<Ticket> b = pool.submit(() -> g2.admit(new Car("RACE-B")));
        int wins = 0;
        for (Future<Ticket> f : List.of(a, b)) { try { f.get(); wins++; } catch (ExecutionException e) { System.out.println("loser: " + e.getCause().getMessage()); } }
        pool.shutdown();
        System.out.println("race winners = " + wins + " (must be 1)");
        if (wins != 1) throw new AssertionError("double-booking!");
        System.out.println("lost ticket fee: " + lot.reportLost(wins == 1 && !a.isCancelled() ? plateOf(a, b) : "RACE-A", new CashPayment(), 200));
    }
    static String plateOf(Future<Ticket> a, Future<Ticket> b) throws Exception {
        try { return a.get().vehicle.plate; } catch (ExecutionException e) { return b.get().vehicle.plate; }
    }
}

Recorded output: parked at F1-C1, expected: Lot full for CAR, fee for car: 20.0, loser: Lot full for CAR, race winners = 1 (must be 1). The full file is at lld/parking-lot/Main.java; javac Main.java && java Main reproduces it.

Concurrency -- the part that makes you "safe"

They almost always push on the race: two cars, one last spot. Naively both threads see it free and both assign. The critical section is find plus occupy plus assign, which is why the lock lives in the lot and not in the gate. Then the two upgrades you name without being asked: one global lock serialises every gate, so a lock per floor or per size bucket lets floors park in parallel; and the lock-free version makes each spot's occupant an AtomicReference<Vehicle> and does a compare-and-set from null to the vehicle, trying the next spot on failure -- more throughput, more code. In a distributed lot the same atomic assign becomes a conditional database update.

SOLID, mapped to this design

SSpot tracks its own occupancy, Floor its spots, Lot orchestrates, Strategy prices. No class does all of it.
OA new pricing or assignment rule is a new class and zero edits to the lot -- Stage 4 proves it.
LAny PricingStrategy drops in for another; the lot never checks the concrete type.
IInterfaces are one method each; a payment class is never forced to implement pricing.
DThe lot depends on interfaces handed to it through configure, never on FlatHourlyPricing directly.

Decisions and complexity

DecisionWhy, and the trade
SpotType enum, not spot subclassesEnough until a size gains real behaviour -- an EV spot with a charger is when the subclass pays.
Map of size to deque, not a scanned listO(1) find and free against O(n); a few pointers of memory.
Singleton lotOne source of truth; the cost is testability. In tests, inject the lot instead of calling getInstance.
Global lock firstSimplicity now; name per-floor and CAS as the upgrades.
Ticket remembers its floorUnpark is O(1) instead of scanning floors for the spot's home.

Big-O: park is O(floors) to scan plus O(1) to take a spot; unpark O(1); availability O(floors x sizes); memory O(spots plus active tickets).

Extension 1 -- "Pricing is 1.5x on weekends, starting now."

Change as little as possible. Count the files you touched.

Reference
Thinking: pricing is a Strategy, so this is a new class and one changed line at the call site; lot, floors, spots and tickets do not move. Wrapping the old rule instead of rewriting it is a Decorator. That relief is the whole reason the interface existed.
// new rule live: 1.5x on weekends. A NEW class + one line — nothing else changes.
class WeekendSurgePricing implements PricingStrategy {
    private final PricingStrategy base;                    // wrap the existing rule (Decorator)
    WeekendSurgePricing(PricingStrategy base) { this.base = base; }
    public double price(Ticket t) {
        double p = base.price(t);
        DayOfWeek d = Instant.ofEpochMilli(t.exitMs)
                             .atZone(ZoneId.systemDefault()).getDayOfWeek();
        boolean weekend = (d == DayOfWeek.SATURDAY || d == DayOfWeek.SUNDAY);
        return weekend ? p * 1.5 : p;
    }
}

Extension 2 -- "A driver lost the ticket. What happens?"

They want the flow, the state, and the code.

Reference
Thinking: duration cannot be computed, so bill a flat daily cap. The ticket is a small state machine -- ISSUED, PAID, LOST, CLOSED -- and lost is one transition that charges the cap and frees the spot, not a special case sprinkled through unpark.
    // lost ticket: bill the daily cap, free the spot, close it -- one transition, no special-casing elsewhere
    double reportLost(String plate, PaymentProcessor payment, double dailyCap) {
        lock.lock();
        try {
            Ticket t = active.remove(plate);
            if (t == null) throw new NoSuchElementException("No active ticket: " + plate);
            t.exitMs = System.currentTimeMillis();
            t.status = TicketStatus.LOST;
            if (!payment.pay(dailyCap)) throw new IllegalStateException("Payment failed");
            t.status = TicketStatus.CLOSED;
            t.spot.release();
            t.floor.vacate(t.spot);
            return dailyCap;
        } finally { lock.unlock(); }
    }

Extension 3 -- "Ten entry gates, and the app needs 'is it full for a truck' every second."

Gates are actors; availability must not scan spots.

Reference
Thinking: gates are thin: they call park and unpark; the logic and the lock stay in the lot, which is exactly why ten gates are safe. Availability is O(1) per floor per size off the free counts the floor already keeps -- the map of counts is why nobody scans.
// entry / exit gates: thin actors. Real logic + the lock live in the lot,
// which is exactly why concurrent gates are safe.
class EntryGate {
    private final ParkingLot lot;
    EntryGate(ParkingLot lot) { this.lot = lot; }
    Ticket admit(Vehicle v) { return lot.park(v); }        // print ticket, open barrier
}
class ExitGate {
    private final ParkingLot lot;
    ExitGate(ParkingLot lot) { this.lot = lot; }
    double checkout(String plate, PaymentProcessor pay) {  // charge, then open barrier
        return lot.unpark(plate, pay);
    }
}
    // availability -- O(1) off the per-size free counts
    Map<SpotType, Integer> availability() {
        Map<SpotType, Integer> total = new EnumMap<>(SpotType.class);
        for (SpotType st : SpotType.values()) total.put(st, 0);
        for (ParkingFloor f : floors)
            for (SpotType st : SpotType.values())
                total.merge(st, f.freeCount(st), Integer::sum);
        return total;
    }
    boolean isFullFor(VehicleType v) {
        for (ParkingFloor f : floors)
            for (SpotType st : Fit.ORDER.get(v))
                if (f.freeCount(st) > 0) return false;
        return true;
    }

The miss log

What they will grill, with the two-breath answers

QuestionAnswer
Why a lock in the lot and not the gate?The invariant is one free spot, one vehicle; it lives where the spot state lives. A lock per gate protects nothing shared.
One global lock -- ten gates queue?Yes. Upgrade one: lock per floor or per size bucket. Upgrade two: CAS on the spot's occupant, try the next spot on failure.
Why a deque and not a list of spots?Head is the next free spot: peek O(1), poll O(1), push O(1). A list means scanning.
Singleton -- how do you test it?Do not call getInstance inside anything; pass the lot in. The singleton is a convenience at the edge, not a dependency in the middle.
Why does the ticket store the floor?So unpark never searches: O(1) to the spot's home.
Truck needs two adjacent spots?Adjacency link on spots, a contiguous run in assignment, a list of spots on the ticket, and all-or-nothing occupy under the lock.
Where would Factory go?Nowhere yet. When spots or vehicles are created from config strings and the creation logic grows, SpotFactory.create earns a place.
Persistence?A repository interface behind the services; the maps become a database table. Services unchanged.

■

Where this stops being true

  • A real round may give 90 to 120 minutes and expect tests. The 60 here is deliberately tight: it trains the skeleton to come out fast.
  • The global lock is correct and slow. At ten gates and thousands of spots the per-floor lock or CAS is the real answer; name it unprompted.
  • Ticket ids from a static counter are process-wide; two lots in one process would share the sequence. Fine here, wrong in a multi-tenant service.
  • Prices are doubles for readability. Money in a real system is an integer of minor units.
  • Nothing here persists. A crash forgets every ticket -- the repository extension is where that answer starts.
