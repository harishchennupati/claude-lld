# Design guidance per system (read with LLD-SPEC.md). slug -> source json ~/answers/system-design/_pipeline/sd_src/lld-<slug>.json

## vending  "Vending Machine"
Root: VendingMachine owning Inventory (slot -> product, count) and the money state. Critical step: dispense = under the lock, re-check stock, take money (inserted >= price), decrement stock, compute change with a ChangeStrategy (greedy by denomination; fails when coins run out -> refund, dispense nothing). State machine IDLE / HAS_MONEY / DISPENSING / OUT_OF_SERVICE; illegal moves throw (insert coin while dispensing). Rules that change: pricing (discount Decorator), change-making, payment (coins, card: PaymentProcessor). O(1): EnumMap<Coin,Integer> for the coin box, map slot->Slot. Observer: display + restock alert when a slot hits zero. Race: two buttons for the last item at once: one dispenses. Tests: last item race, exact change impossible -> refund and stock unchanged, cancel returns exactly what was inserted, card decline leaves stock, restock updates count, throwing display listener harmless, illegal transition rejected. Twists: multiple currencies, hold item then pay (reservation with expiry), telemetry, admin restock role, persistence of the coin box.

## atm  "ATM"
Root: ATM session per card (a Session object) talking to a BankService interface (balance, debit with an idempotency key) and a CashDispenser. Critical step: withdraw = validate PIN (3 tries then card retained), check amount is a multiple of notes available, ASK THE BANK TO DEBIT with an idempotency key, only on success dispense notes; if dispensing fails after the debit -> compensating credit (or a reversal record) so the customer never loses money; a timeout from the bank = UNKNOWN: do not dispense, reconcile. State machine per session: CARD_INSERTED / AUTHENTICATED / TRANSACTION / DISPENSING / EJECTED; per transaction PENDING / DEBITED / DISPENSED / REVERSED. Rules that change: note-selection strategy (fewest notes), limits per day, fee policy. O(1): EnumMap<Note,Integer> cassette counts. Observer: receipt printer, audit log. Race: two sessions on the same account withdrawing near the balance: the bank's debit is the single writer (conditional UPDATE balance >= amount). Tests: wrong PIN three times retains the card, insufficient cassette refuses BEFORE debit, bank decline dispenses nothing, dispenser failure after debit produces a reversal, bank timeout dispenses nothing and records UNKNOWN, note selection exact, throwing printer harmless. Twists: deposit with envelope/verification, mini-statement, multi-bank network (switch), offline mode limits, persistence/reconciliation file.

## rate-limiter  "Rate Limiter"
Root: RateLimiter with a RateLimitAlgorithm strategy (token bucket, sliding window log, sliding window counter, fixed window) and per-key state in a map. Critical step: allow(key) = under the key's lock (a striped lock or a lock per bucket), refill by elapsed time from an injected Clock, then take a token or refuse; must be O(1) per call. State: Bucket{tokens (double or long micro-tokens), lastRefillMs}; window counter {currentCount, previousCount, windowStart}. Rules that change: the algorithm, the limit per tier (config Decorator), what to do on refuse (reject vs queue). O(1): ConcurrentHashMap<key,Bucket>, per-bucket lock; sliding log is O(log n) or O(n) -> say why it is the accurate but expensive one. Observer: metrics (allowed/refused counters). Race: 100 threads hitting one key at the limit: exactly `limit` allowed. Tests: burst then refill by injected clock, boundary of fixed window (2x burst at the edge, why sliding fixes it), 100-thread race exactly N allowed, unknown key gets a fresh full bucket, eviction of idle keys, clock going backwards does not mint tokens, throwing metrics listener harmless. Twists: distributed limiter (Redis INCR + TTL, Lua script for atomicity), per-user vs per-IP vs global, weighted costs per request, warm-up, shadow mode, back-pressure/queueing with deadline.

## lru  "LRU / LFU Cache"
Root: LruCache<K,V> = HashMap<K,Node> + doubly linked list (head = most recent), capacity; get moves to head O(1); put inserts or updates, evicts tail when full. Then LFU: frequency lists (map freq -> LinkedHashSet or a DLL per freq) with minFreq tracking, O(1). Critical step: put when full = evict tail then insert, under one lock (or a ReadWriteLock; discuss why LRU's get is a write). Rules that change: eviction policy behind an interface (LRU, LFU, FIFO, TTL Decorator), the loader (read-through), the listener on eviction. O(1) everything; state: node {key,value,prev,next,freq,expireAt}. Observer: eviction listener, stats (hits/misses). Race: two threads get/put at capacity: size never exceeds capacity, no node lost. Tests: order after gets, eviction of the right key, update keeps one node, capacity 1, 50-thread race size <= capacity and all keys either present or evicted (count), TTL expiry with injected clock, LFU tie broken by recency, throwing eviction listener harmless. Twists: thread-safe without a global lock (segments/striping), weighted entries by size, TTL sweeper vs lazy, write-behind to a store, LinkedHashMap accessOrder (say when it is enough), Caffeine's W-TinyLFU as the real-world answer.

## logger  "Logger"
Root: Logger with a level, a list of Appenders (console, file, rolling file, async), a Formatter, and a LoggerContext (hierarchy by name: com.app.db inherits from com.app). Critical step: log(level, msg) = level check first (cheap, no lock), format lazily (only if any appender accepts), hand the event to appenders; the async appender puts on a bounded queue and a single writer thread drains it (never lose the ordering within one thread; on a full queue: block, drop with a counter, or discard oldest, a configurable policy). Rules that change: format, appenders, level per logger at runtime, the overflow policy. O(1): level as an enum ordinal compare, map name -> logger. Observer: the appenders ARE observers; error handler on appender failure. Race: 50 threads logging at once into the async appender: all lines present, none torn, per-thread order kept. Tests: level filter, hierarchy inheritance, lazy formatting (a counter shows format not called when filtered), rolling file rotates at size, bounded queue drop policy counts drops, shutdown flushes everything, throwing appender does not stop the others. Twists: structured logging (JSON key-value), MDC/context per thread, sampling, log4j-style config reload, log shipping (the appender as a client), why System.out is slow (a lock per println).

## tic-tac-toe  "Tic-Tac-Toe"
Root: Game owning a Board (n x n), two Players, the turn, the status; Move validation; WinChecker strategy (O(1) per move using row/col/diagonal counters instead of scanning the board); state machine IN_PROGRESS / X_WON / O_WON / DRAW; move after end throws; undo stack (Command). Rules that change: board size, win length k, the player kind (human, random bot, minimax bot: Strategy), the checker. O(1): counters rowCount[n], colCount[n], diag, antiDiag per player. Observer: a display/spectator, a game recorder. Race: two moves submitted at once for the same turn: one applied (the game's lock). Tests: win by row/col/diag with counters, draw detection, wrong turn rejected, occupied cell rejected, undo restores counters, minimax never loses from an empty board (short run), 50-thread race only one move applied per turn. Twists: n x n with k-in-a-row, replay from move list, multiple simultaneous games (a GameService with a map), timers per move, persistence of the move log, Connect-4 as the same shape with gravity.

## chess  "Chess"
Root: Game owning Board (8x8 of Piece or null), two Players, the turn, the move history (Command with undo), the status. Pieces: abstract Piece with `List<Move> legalMoves(Board, from)` per subclass (Pawn, Rook, Knight, Bishop, Queen, King), sliding pieces share a helper; a Move records from, to, captured, promotion, castle/en passant flags. Critical step: makeMove = generate pseudo-legal, apply, verify own king not in check, else undo and reject; state machine ACTIVE / CHECK / CHECKMATE / STALEMATE / DRAW (50-move, repetition as twists). Rules that change: variants (a rule set interface), time control, the AI player. O(1)/bounded: board array, king positions cached, attack check bounded by 8 directions + knight offsets. Observer: spectators, clock. Tests: knight moves from corner = 2, pawn double step only from start, cannot move into check, castling refused through check, en passant window, checkmate detected (fool's mate), stalemate detected, undo restores captured piece. Twists: move generation performance (bitboards named), PGN import/export, draw rules, online play (a Match service, persistence of the move list, reconnection), Elo.

## snake-ladder  "Snake and Ladder"
Root: Game owning Board (size, map cell -> jump destination: snakes down, ladders up), players in a Deque (turn rotation O(1)), Dice strategy (fair, loaded for tests, injected random), status. Critical step: takeTurn = roll, compute target, apply the jump table once (no chaining unless a rule says so), exact-landing rule to win, rotate the queue; a game after WON rejects turns. State: WAITING / IN_PROGRESS / FINISHED; player position. Rules that change: dice count, exact-finish rule, extra turn on six, board layout. O(1): HashMap<Integer,Integer> jumps, ArrayDeque turns. Observer: board display, commentary. Tests: ladder up and snake down, exact landing needed (overshoot stays), win ends the game, turn order rotates, loaded dice makes the test deterministic, a snake head cannot be a ladder base (validation), no snake at cell 100. Twists: many players, multiple dice, a bot deciding among dice, timers, persistence of turns, network play with a turn token.

## notification-lld  "Notification Service (LLD)"
Root: NotificationService owning channel adapters (Channel interface: send(message) -> Result), a Router (preferences, quiet hours, cap), a Deduper (idempotency key with TTL), a RetryPolicy (Strategy: fixed/exponential with cap), a bounded queue + worker pool, and a Store of notification states. Critical step: submit = dedupe under the key's lock, persist QUEUED, enqueue; a worker sends OUTSIDE any lock, then records SENT/FAILED/UNKNOWN idempotently; retry schedules by the policy; expiry drops. State machine QUEUED / SENT / UNKNOWN / DELIVERED / FAILED_RETRYABLE / FAILED_FINAL / EXPIRED with rank-based idempotent updates. Rules that change: channel, retry policy, rate limit per channel (token bucket), template rendering. O(1): maps by id, per-channel queues. Observer: receipts webhook -> state update, metrics. Race: the same key submitted by 50 threads: one queued. Tests: dedupe race, retry with injected clock and backoff sequence, expiry drops before send, rank-based update ignores an older receipt, quiet hours defer, cap per day reserve/release on failure, throwing channel isolated. Twists: priority lanes, batching for email, campaign pacing, persistence/outbox, exactly-once impossibility explained in code.

## file-system  "In-memory File System"
Root: FileSystem owning a Directory tree (Directory{name, children map, parent}, File{name, content, size}), path resolution by splitting on '/', a Composite (Node interface: size(), listing). Critical step: create/move/delete under the tree's lock (or a lock per directory with parent-first ordering to avoid deadlock; say why global first), permissions check (Strategy: owner/mode bits). O(1)/O(depth): HashMap children, path walk O(depth). State: a file's open handles (reference count) so delete while open is refused or deferred. Rules that change: permission model, size accounting (Decorator counting quota), search (Visitor). Observer: watchers (inotify-like) on a directory. Race: 50 threads creating files in one directory: all present, unique names enforced. Tests: mkdir -p semantics, move into own subtree rejected, delete non-empty dir refused unless recursive, quota exceeded refuses write and size unchanged, path with .. resolves, watcher notified after unlock, throwing watcher harmless, race creates exactly N files. Twists: symlinks and cycle prevention, hard links (inode split), persistence (journal), large files as chunks, concurrent readers/writer per file (ReadWriteLock), search by name/size/extension with a filter chain.

## stackoverflow  "Stack Overflow"
Root: QAService owning Users, Questions (title, body, tags, answers, votes, accepted answer), Answers, Comments, a VoteLedger (one vote per user per post, changeable), Reputation rules (Strategy: +10 upvote on answer, +5 question, -2 downvote, accept +15), a TagIndex, a SearchIndex (inverted map word -> posts). Critical step: vote = under the post's lock, check the ledger (idempotent: same vote twice = no-op; flip = -2 then +1 effects), update score and reputation atomically; accept answer = only the question owner, only one accepted. State machine for a question OPEN / CLOSED / DELETED, and bounties. O(1): maps by id, score kept, not recomputed. Observer: notifications to the author, reputation events. Race: 50 threads voting on one answer: score == distinct voters. Tests: duplicate vote no-op, flip vote net effect, accept by non-owner refused, second accept replaces the first (reputation adjusted), closed question rejects answers, search finds by word, reputation privileges unlock at thresholds, throwing notifier harmless. Twists: edit history, moderation queue, badges (Observer on events), pagination and sort strategies, persistence, caching hot questions, spam rate limit.

## order-book  "Order Book / Matching Engine (LLD)"
Root: OrderBook per symbol: bids as TreeMap<price DESC, ArrayDeque<Order>> and asks as TreeMap<price ASC, Deque>, an index orderId -> Order (for O(1) cancel via a doubly-linked queue or lazy deletion), price-time priority. Critical step: submit = under the book's lock (one thread owns a symbol), match against the opposite side while prices cross, emit Fills (Observer: trade listener), rest the remainder (limit) or cancel it (IOC/FOK: FOK checks fillable quantity first without mutating). State machine per order NEW / PARTIALLY_FILLED / FILLED / CANCELLED / REJECTED. Rules that change: order types (Strategy per type), self-trade prevention, tick size validation. O(1)/O(log n): best price = firstEntry, cancel O(1) with a linked node. Race: 50 threads submitting crossing orders: total filled quantity conserved (sum of buys filled == sum of sells filled). Tests: price-time priority (earlier order at same price fills first), partial fill leaves remainder resting, market order sweeps levels, FOK all-or-nothing, cancel of a resting order, self-trade prevention, invariant conservation under race, no negative quantity. Twists: iceberg, stop orders (trigger list), replace keeps/loses priority, snapshot/replay of the event log, sharding by symbol, determinism for replay.

## pubsub  "Pub/Sub System"
Root: Broker owning Topics (name -> Topic{partitions or a single log, subscribers}), Subscriber{id, offset, handler}, a Message log per topic (ArrayList/ArrayDeque with retention), delivery by a dispatcher thread per subscriber (pull by offset) or push. Critical step: publish = append under the topic's lock, assign offset, then signal dispatchers (after unlock); consume = read from the subscriber's offset, ack advances the offset (at-least-once: redeliver if no ack within a timeout; idempotent handlers). State: subscriber ACTIVE / PAUSED / DEAD; message offsets. Rules that change: delivery semantics (at-most / at-least once), retention policy, partitioning key, ordering (per key). O(1): append, offset lookup by index. Observer: it IS the pattern; plus metrics on lag. Race: 50 publishers to one topic: offsets contiguous, no message lost, per-publisher order kept. Tests: fan-out to N subscribers, offset resume after subscriber restart, ack advances, no-ack redelivers once with injected clock, retention drops the oldest and a lagging subscriber gets an error, a slow subscriber does not block others, throwing handler isolates. Twists: consumer groups (partition assignment), dead-letter, back-pressure, persistence to disk (segment files), exactly-once via idempotent keys, Kafka mapping of every class.

## ride-sharing  "Ride Sharing (Uber LLD)"
Root: RideService owning Riders, Drivers (status AVAILABLE / ON_TRIP / OFFLINE, location), Trips, a Matching strategy (nearest available by distance via a simple grid index: cell -> drivers), a Pricing strategy (base + per km + surge Decorator), a Payment processor. Critical step: requestRide = find candidates from the grid, then CLAIM a driver atomically (driver's state AVAILABLE -> ASSIGNED under the driver's lock or a CAS on an AtomicReference<status>); two riders requesting the same nearest driver: exactly one gets him; trip state machine REQUESTED / ASSIGNED / STARTED / COMPLETED / CANCELLED with cancellation rules (fee after driver en route). O(1): grid cells map, maps by id. Observer: rider and driver notifications, ETA updates. Tests: nearest driver chosen, two riders one driver race one winner, cancel before start frees the driver, complete computes fare with injected clock/distance, surge decorator multiplies, payment fails leaves trip COMPLETED_UNPAID for retry, driver offline never matched, throwing notifier harmless. Twists: geo-index (quadtree/geohash named), driver acceptance timeout then next candidate, pooling, rating, persistence, real-time location updates rate.

## food-delivery  "Food Delivery (Swiggy LLD)"
Root: OrderService owning Restaurants (menu, open hours, prep time), Carts, Orders, DeliveryPartners, an Assignment strategy, a Pricing strategy (item total + delivery fee + surge + coupon Decorator chain), a Payment processor, a Notification observer. Critical step: placeOrder = validate cart against the live menu/availability, price it, take payment (outside the restaurant lock), then create the order PLACED and notify the restaurant; the restaurant accepts/rejects (state ACCEPTED / PREPARING / READY / PICKED_UP / DELIVERED / CANCELLED); assignment claims a partner atomically (as in ride sharing). Rules that change: pricing/coupons, assignment, cancellation policy (refund rules by state). O(1): maps by id, per-restaurant order queue. Race: two orders taking the last stock of an item: one succeeds (item stock decrement under the restaurant lock). Tests: unavailable item rejects the whole order, coupon chain math (percent then flat, cap), payment decline creates no order, cancel after PREPARING charges fee, partner claim race one winner, delivery state cannot skip steps, throwing notifier harmless. Twists: ETA model, multi-restaurant cart, scheduled orders, partner pooling, persistence and the outbox for notifications, idempotent placeOrder on retry.

## text-editor  "Text Editor"
Root: Editor owning a Document (a text buffer: start with StringBuilder, then a gap buffer or piece table as the real answer), a Cursor/Selection, an UndoStack of Commands (insert, delete, replace, each with inverse), a Clipboard, Formatting (a Decorator/Flyweight for character styles). Critical step: every edit is a Command: execute mutates the buffer and records the inverse; undo/redo are stacks; a macro is a composite command. Rules that change: buffer implementation (Strategy), key bindings, rendering. O(1) amortised insert at the cursor with a gap buffer; O(log n) with a rope (named). Observer: views/renderers, autosave. Race: single-writer document; concurrent viewers use snapshots (say why an editor is not multithreaded on the buffer). Tests: insert/delete/undo/redo sequences restore exact text, redo cleared after a new edit, gap buffer moves the gap correctly on cursor jumps, selection delete as one command, find/replace all as one undoable command, autosave observer called after unlock, throwing view harmless. Twists: collaborative editing (OT vs CRDT named, not built), large files (piece table over a mmap), syntax highlighting incremental, plugin hooks, persistence (journal of commands).

## spreadsheet  "Spreadsheet"
Root: Sheet owning Cells (map "A1" -> Cell{raw, value, formula AST, dependents set, precedents set}), a Parser (tokens -> AST: numbers, refs, ranges, + - * / and functions SUM/AVG/MIN/MAX), an Evaluator (Interpreter pattern), a dependency graph for recomputation (topological order via Kahn from the changed cell; a cycle is detected and reported as #CYCLE without corrupting other cells). Critical step: setCell = parse, detect cycle BEFORE committing (dry-run on the graph), then update precedents/dependents, then recompute dependents in topological order; all under the sheet's lock. Rules that change: functions (a registry), number formats, the evaluation strategy (eager vs lazy). O(1)/O(deps): maps, only dependents recomputed. Observer: cell change listeners (UI). Tests: SUM over a range, chain A1->B1->C1 recomputes in order, cycle rejected and old values kept, delete a referenced cell yields #REF, string vs number, 50-thread race setting different cells leaves every formula consistent, throwing listener harmless. Twists: lazy evaluation with dirty flags, ranges of thousands of cells (interval trees named), undo, persistence, collaborative edits, volatile functions (NOW()).

## digital-wallet  "Digital Wallet"
Root: WalletService owning Accounts (balance in long paise, currency, status), a Ledger of immutable entries (double-entry: every transfer = debit entry + credit entry with the same txn id), Transactions with an idempotency key, a FraudCheck strategy, a Limits strategy (daily cap). Critical step: transfer = validate, check idempotency (same key -> return the same result), lock both accounts in a fixed order (by id, to avoid deadlock), check balance, write both ledger entries and update both balances atomically, release; a failed step leaves both untouched. State machine per transaction PENDING / COMPLETED / FAILED / REVERSED; account ACTIVE / FROZEN / CLOSED. O(1): maps by id, balance cached from ledger. Observer: notifications, fraud alerts. Race: 50 threads transferring between two accounts in both directions: the sum of balances is conserved and no deadlock. Tests: conservation under race, insufficient balance changes nothing, idempotent retry returns the same txn, frozen account refuses, daily limit, reversal creates opposite entries (never edits), ledger replay reproduces balances, throwing notifier harmless. Twists: top-up via a payment gateway (UNKNOWN state and reconciliation), multi-currency with FX at the moment of transfer, persistence with a conditional UPDATE version column (optimistic locking), audit/immutability, settlement with a bank.

## banking  "Banking System"
Root: Bank owning Customers, Accounts (Savings/Current subclasses with rules: minimum balance, overdraft), a Transaction ledger, interest rules (Strategy per account type, applied by a scheduler with an injected clock), a Statement generator. Critical step: transfer as in digital-wallet (ordered locks, atomic debit+credit, idempotency); withdrawal honours minimum balance / overdraft rule (Template Method or Strategy). State: account OPEN / DORMANT / FROZEN / CLOSED; transaction states. O(1): maps, running balance. Observer: alerts (large withdrawal), statements. Tests: overdraft allowed only on Current, minimum balance on Savings, interest computed for a period with the injected clock, transfer race conservation, dormant after N days without activity (clock), close with balance refused, idempotent transfer, throwing alert harmless. Twists: joint accounts (two owners, approval), scheduled payments, loans/EMI as a schedule, KYC states, persistence/audit, multi-branch consistency.

## inmem-db  "In-memory Database (SQL-like)"
Root: Database owning Tables (name -> Table{columns with types, rows list, primary key index HashMap, secondary indexes TreeMap for range}), a Query object model (select with where predicate, insert, update, delete), constraints (PK unique, NOT NULL, FK optional), and Transactions with a simple lock-based isolation (table-level lock or row versions). Critical step: insert = validate types and constraints, then write row and indexes atomically under the table lock; a constraint failure changes nothing; update maintains indexes (remove old key, add new). O(1)/O(log n): PK lookup via HashMap, range via TreeMap. Rules that change: index types, isolation level, the predicate language. Observer: triggers (after insert) called after unlock. Race: 50 threads inserting into a PK table: no duplicate PK, count exact. Tests: PK duplicate rejected, type check, index maintained on update, range query via TreeMap, delete removes from indexes, transaction rollback restores, race PK uniqueness, throwing trigger harmless. Twists: MVCC (versions per row, snapshot reads), WAL persistence, joins (nested loop vs hash join), query planner choosing an index, sharding by PK.

## cache-eviction  "Cache with Eviction Policies"
Root: Cache<K,V> with an EvictionPolicy interface (onGet, onPut, evictKey) and implementations LRU (DLL), LFU (frequency lists), FIFO (queue), TTL (expiry heap + lazy check), plus a Storage map; a Loader for read-through; stats. Critical step: put when full = policy.evictKey() then store, under one lock; get = storage lookup then policy.onGet. Rules that change: the policy (Strategy), TTL Decorator over any policy, size-aware weights. O(1) for LRU/LFU/FIFO; TTL O(log n) with a heap. Observer: removal listener with cause (EVICTED / EXPIRED / EXPLICIT). Race: 50 threads: size <= capacity always, no lost node. Tests: each policy's eviction order on the same access trace, TTL expiry with injected clock, removal cause reported, stats hit ratio, race size bound, policy swap at runtime keeps entries, throwing listener harmless. Twists: segmented/striped locks, W-TinyLFU (Caffeine) named and sketched, admission policy (do not cache one-hit wonders), write-back, distributed variant (consistent hashing named).

## payment-gateway  "Payment Gateway (LLD)"
Root: PaymentService owning Payments (id, idempotency key, amount in paise, currency, state), Merchants, a PaymentMethod strategy (card, UPI, wallet: each a Processor adapter to an external network), a Router (which processor for which method/bank, with failover), a WebhookHandler for async results, a Refund flow, a Reconciliation job. Critical step: pay = idempotency check, create PENDING, call the processor OUTSIDE the lock with a timeout, then record SUCCESS/FAILED/UNKNOWN; UNKNOWN is never retried blindly: it is queried (status API) or reconciled; refunds are separate transactions linked to the payment and never exceed the captured amount. State machine CREATED / PENDING / AUTHORIZED / CAPTURED / FAILED / UNKNOWN / REFUNDED (partial), with rank-based idempotent updates from webhooks arriving out of order. Rules that change: routing, retry policy per processor, fees. O(1): maps by id and by idempotency key. Observer: merchant webhook notifications with retries. Race: 50 threads paying with the same idempotency key: one processor call. Tests: idempotent pay, processor timeout -> UNKNOWN and no second call, status query resolves UNKNOWN, refund over amount refused, partial refunds sum to the cap, webhook out-of-order ignored by rank, router failover on processor down, throwing merchant webhook isolated. Twists: 3DS/OTP flow (a pause in the state machine), settlement and payouts, PCI scope (tokenisation), persistence/outbox, ledger double entry, chargebacks.

## mt-blocking-queue  "Bounded Blocking Queue"
Root: BoundedBlockingQueue<T> with a ReentrantLock and two Conditions (notFull, notEmpty), an array ring buffer (head, tail, count). Critical step: put = lock; while (count == capacity) notFull.await(); enqueue; notEmpty.signal(); unlock; take mirrors it. Why `while` (spurious wakeups), why two conditions (a single notify can wake the wrong side), why signal not signalAll (thundering herd) and when signalAll is needed. Then the variants: timed offer/poll with awaitNanos, interruptible waits, a synchronized/wait/notify version (and its lost-wakeup pitfall), a lock-free MPSC ring (named). Moves for MT: nouns -> the queue and its two waiting parties; the invariant (0 <= count <= capacity, FIFO); shared state -> one lock; the wait protocol (check under lock, wait in a loop, signal after the change); what is inside the lock; N producers/consumers at once; ladder: one lock two conditions -> two locks (LinkedBlockingQueue style, put lock + take lock with atomic count) -> lock-free. Tests: FIFO order with one producer one consumer, 10 producers 10 consumers 100k items all delivered once (counts), blocking when full and unblocking on take (latch + timeout), timed poll returns null after the timeout with an injected/real clock, interrupt wakes a waiter with InterruptedException, capacity 1 works, no lost wakeup under a stress loop. Twists: priority queue variant, fairness, drain-to, bounded by bytes not count, back-pressure as the reason to bound.

## mt-producer-consumer  "Producer-Consumer"
Root: the pipeline: N producers, a bounded buffer (reuse the blocking-queue idea but built here: wait/notify version first, then Lock+Conditions, then java.util.concurrent.BlockingQueue), M consumers, a poison-pill shutdown protocol (one pill per consumer or a shared shutdown flag with drain), and a result collector. Critical step: the hand-off and the shutdown: consumers must drain remaining items after the stop signal; producers must not add after stop. Moves: invariant (every produced item consumed exactly once), shared state, the wait protocol, inside-the-lock, ladder (wait/notify -> two conditions -> j.u.c queue -> Disruptor named). Tests: exactly-once delivery count under 10x10 threads, shutdown drains everything (no item left, no consumer stuck), poison pill count equals consumers, a slow consumer applies back-pressure (producer blocks; measured with a latch), interruption handled, exceptions in a consumer do not lose the item (retry or dead-letter). Twists: batching, priority, multiple queues by key (ordering per key), work stealing (ForkJoin named), backpressure to an upstream network client.

## mt-rwlock  "Read-Write Lock"
Root: a ReadWriteLock built from a ReentrantLock + Conditions (or synchronized): readers count, writer flag, waiting writers count; readLock: wait while a writer holds or (writer preference) writers are waiting; writeLock: wait while readers > 0 or writer active. Policies: reader-preference (writer starvation), writer-preference, fair (FIFO with a queue of tickets). Reentrancy for the writer; lock downgrading (write -> read) allowed, upgrading (read -> write) deadlocks unless special. Moves: invariant (many readers XOR one writer), shared state, the wait protocol, ladder (one lock -> two conditions -> StampedLock optimistic reads named). Tests: many readers concurrently (measured overlap with a latch), a writer excludes readers, writer preference starves no writer (a waiting writer gets in before new readers), fairness order with a ticket, downgrade works, upgrade attempt detected/refused, interrupt while waiting, stress: a shared counter incremented by writers and read by readers is never torn. Twists: StampedLock optimistic read pattern, timed lock, condition support, distributed RW lock (named), when a ConcurrentHashMap beats a lock.

## mt-ttl-cache  "TTL Cache (thread-safe)"
Root: TtlCache<K,V> with a ConcurrentHashMap<K,Entry{value, expireAt}>, an injected Clock, lazy expiry on get, plus an active sweeper: a single background thread (ScheduledExecutor) with a min-heap/TreeMap of expiries, removing entries whose expireAt passed; put with TTL, get, remove; compute-if-absent with a loader that is called ONCE per key under contention (the map's atomic compute or a per-key future). Critical step: the loader race (many misses for one key -> one load), and expiry vs a concurrent refresh (compare the entry identity before removing: remove(key, entry)). Moves: invariant (no expired value is ever returned; a key is loaded at most once per miss window), shared state, the wait protocol (future per key), inside the lock (CHM's per-bin lock), ladder (global lock -> CHM + per-key future -> sharded sweepers). Tests: expiry by injected clock, sweeper removes without touching live entries, 50 threads miss the same key: loader called once, refresh does not get removed by a stale sweep (identity check), get after remove is null, TTL 0 means no cache, sweeper survives a throwing loader. Twists: refresh-ahead, jitter on TTL, size bound + LRU (Caffeine named), metrics, distributed invalidation.

## mt-striped-map  "Striped (segmented) Concurrent Map"
Root: StripedMap<K,V> with N segments (each a HashMap + its own ReentrantLock, or synchronized), segment = hash(key) & (N-1); get/put/remove lock one segment; size() sums per-segment counts (approximate) or locks all in order; resize per segment. Critical step: the per-segment lock scope and the all-segment operations (size, clear, iteration snapshot) with ordered locking to avoid deadlock. Moves: invariant (a key lives in exactly one segment; per-key linearizable ops), shared state, ladder (one lock -> stripes -> CHM's per-bin locks + CAS on empty bins -> lock-free). Tests: 50 threads put distinct keys count exact, same key from many threads last-writer-wins and no lost entry, computeIfAbsent runs once per key, size after concurrent adds exact when computed under all locks, iteration snapshot does not throw ConcurrentModification, stripe count power of two, stress no deadlock in size() with concurrent puts. Twists: read without lock (volatile/immutable entries), resize under load, weak keys, why ConcurrentHashMap does it differently (Java 8: bins + CAS + synchronized on bin head), memory overhead per stripe.

## mt-dining  "Dining Philosophers"
Root: Table with N forks (each a ReentrantLock) and N philosophers (threads) that think, pick up two forks, eat, put down; the deadlock (everyone holds the left fork) and the fixes: resource ordering (always lock the lower-numbered fork first), a waiter/semaphore allowing N-1 at the table, tryLock with backoff (livelock risk), Chandy-Misra (named). Moves: invariant (a fork is held by one; no deadlock; no starvation), shared state, the protocol, inside the lock, ladder (ordering -> waiter -> tryLock). Tests: with the naive protocol a deadlock detector (all blocked for T ms) fires in a bounded run (demonstrated safely with tryLock timeouts, never a real hang), ordered locking runs 10k meals with no deadlock, waiter version never has N eating, each philosopher eats (no starvation) in a fair run, forks released on exception, interrupt while waiting handled. Twists: fairness metrics, asymmetric philosophers, generalise to any resource-ordering problem (bank transfers), detecting deadlocks in production (thread dumps), lock-free alternative.

## mt-h2o  "H2O molecule barrier"
Root: H2O with hydrogen() and oxygen() called by threads; release in groups of 2 H + 1 O; built with a ReentrantLock + Conditions (or Semaphores + a CyclicBarrier of 3): counters of waiting H and O, a barrier that releases a triple, and the rule that no thread passes before its molecule is complete. Moves: invariant (output is groups of HHO in some order, never HHH or HOO), shared state, the wait protocol, ladder (lock+conditions -> semaphores + barrier -> phaser). Tests: 2H+1O for 1000 molecules: every window of three contains exactly two H and one O, no thread released early (a latch check), extra H waits when O is missing, interrupt handled, fairness (no starvation) over a long run, the semaphore version passes the same checks. Twists: general k-of-n barrier, CyclicBarrier reuse and its broken state, Phaser, the Unisex bathroom / building H2O variants, why CountDownLatch cannot be reused.

## mt-print-series  "Print in order (FizzBuzz / odd-even / 0-1-2 by threads)"
Root: a Printer with a shared turn counter and N threads each printing when it is their turn: with wait/notify (single monitor, while loop), with Lock + one Condition per thread (no herd), with Semaphores chained (each thread releases the next). Moves: invariant (output strictly in order; each thread prints only its numbers), shared state, the wait protocol (turn variable checked in a loop), ladder (notifyAll -> per-thread condition -> semaphores). Tests: three threads print 1..300 in order (captured output equals expected), no duplicates, the semaphore version, the condition version, interrupt handling, a slow thread does not break order, 10 threads round-robin. Twists: FizzBuzz multithreaded (4 threads), print with a dynamic set of threads, the producer/consumer connection, why busy-waiting is wrong (CPU), using a Phaser.
