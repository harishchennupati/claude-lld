# LLD workbench spec (locked 2026-09-12/13 on the parking lot; roll to every LLD)

Gold example: `~/answers/lld/parking-lot-workbench.html` (open it in a browser and read all five pages first) built by `~/answers/lld/_build_pl_wb.py`, Java in `~/answers/lld/parking-lot/`. New systems use the engine `~/answers/lld/lld_engine.py`: write `~/answers/lld/specs/<slug>.py` that does `from lld_engine import *`, builds the content with the helpers, and calls `build(spec)`. The engine writes `~/answers/lld/<slug>-workbench.html` and REFUSES to write a page whose Java does not compile or whose test class does not print `ALL PASS`.

Audience: an SDE-2/3 backend engineer, anxious, diagram-first, who reads on a desktop and wants to understand a system in one sitting and then be able to write it from a blank file in an interview. Plain English. Every term defined where it first appears. No interview scripts ("say this"), no quizzes, no "thinking" boxes, no per-class expansion.

## The five pages (exactly five; the engine fixes the frame)

1. **Problem** (`problem_body`): in this order:
   - `<div class="move"><div class="prompt">"the prompt as an interviewer says it, 2-3 sentences, ending with something like 'I want working code, not a diagram. Go.'"</div></div>`
   - `<div class="move"><h3>The problem, in plain words</h3><p>4-7 sentences: what the system is, who uses it, what must happen, the one invariant (e.g. two vehicles must never get the same spot; a seat is sold once; a balance never goes negative).</p></div>`
   - `<div class="move"><h3>What is expected of you in the hour</h3><p>what "working code" means here, and what the interviewer watches for, in order: the questions asked before typing; which classes exist and who owns which state; the main flows end to end; the race; where the rules that change live; the failure that must leave state consistent; then the twists.</p></div>`
   - `<div class="move"><h3>What the code must do</h3></div>` + ONE picture (`_mv`, 1230 wide, ~300 tall): the main flows as rows of boxes with an accent box on the step that decides, a dashed reject/failure branch, and the query/read as a text line; caption line at the bottom stating the concurrency invariant.
   - `<div class="move"><table class="ask"><tr><th>Ask</th><th>Assume this when they say "you decide"</th><th>What the answer decides</th></tr>...6-8 rows, the last column names the move number(s)...</table></div>`
   - `<div class="move"><h3>What it must do, and what it must survive</h3></div>` + `<div class="req"><div><b>Functional requirements</b><ul>5-8 li</ul></div><div><b>Non-functional requirements</b><ul>5-7 li: concurrency invariant, O(1) or bounded lookups, rules swappable, one source of truth, nothing half-done, in memory / one process (say it)</ul></div></div>`
   - `<div class="move"><h3>One afternoon, replayed</h3></div>` + ONE timeline picture (`_card` boxes on a time axis, 4 events) with concrete ids, times and numbers, showing the invariant holding (a reject, a fee, a race decided).
   - `<div class="grade"><b>Say before typing:</b> the assumptions in one breath; named out-of-scope items, each "a follow-up on page 05".</div>`
2. **Derivation** (`derivation_lead`, `moves`): 10-12 moves, each `(title, picture, paragraph)`. The title is "Move N: <the rule in one sentence>". The picture shows the move applied to THIS system (boxes, arrows, a table, a state machine, a timeline), never generic. The paragraph (4-8 sentences, plain) applies the rule to this system's nouns and verbs. The moves, in order, always:
   1 nouns with their own state -> classes (a sentence picture with arrows to boxes; dashed = no state, a caller or a method);
   2 verbs -> the class that owns the state they touch -> methods (verb | owner | method rows);
   3 rules the interviewer can change mid-round -> one-method interfaces handed in (this is where Strategy / Decorator / Observer are BORN; name them here, do not announce them elsewhere);
   4 state that many callers change at once -> one owner and one lock (draw the gap: two callers both see X free);
   5 each collection -> the question asked of it -> the O(1) shape (question | shape | cost rows);
   6 anything with a life cycle -> a state machine + the ORDER of operations at the critical step (what is committed before what, and why a failure leaves things consistent);
   7 what is inside the lock and for how long, and N callers at the same instant (answers "is everything now one by one?");
   8 the arithmetic (how busy the lock is, with the system's own numbers) then the upgrade ladder (3 rungs, cheapest first);
   9 what can go wrong -> a test for each (4-6 rows: failure | fix + test);
   10 the patterns named after the fact (pattern | born in move | the line in the code | what it buys; and the ones NOT earned, e.g. Factory "not yet", Builder "never");
   11 SOLID as a check table (letter | rule in plain words | from which move | the line that shows it);
   12 any twist is one of five moves (a new rule -> new class behind the interface; someone new wants to know -> observer; a new step in a life -> state + transition; a new invariant across items -> same lock; state that must outlive the process -> repository + conditional UPDATE), with the system's real twists as examples.
   Use `_mv(1230,h,_D+...)` with `_bx`, `_ar`, `_tx`, `_card`, `_table`. Every label must fit its box (~7.5 px per char at 12.5px for titles, ~6.3 for sub-labels). Numbers in move 7-8 must be real for this system (e.g. 10 gates, 3 parks/s, 1.5 us inside the lock).
3. **Design** (`uml_svg`, `how_to_read`): the whole class diagram once, built with `uml_reset(); put(id,x,y,w,Name,[fields],[methods],stereo="interface"|"enum"|"" ,abstract=False)` and `ln(B[a][side],B[b][side],kind,label,via)` with kinds inherit / compose / assoc / inject / notify, assembled by `uml_svg(1230,h,edges)`. Italic = abstract, dashed = interface. Layout: enums right, interfaces + implementations right column, the aggregate root top centre, owned classes below it, callers left. `how_to_read`: how to read a box, the arrows, and where state lives (one paragraph).
4. **Code** (`code_intro`, `files`, `test_class`): three files, in this order: `Main.java` (the whole system, one file, compiles alone, ends with a `main` that runs a demo AND a many-thread race with a `CountDownLatch` proving the invariant, printing counts), `Extensions.java` (the reference code for every follow-up: each twist as a small class or method, plus an `ExtDemo` main that exercises them), `FailureTests.java` (6-8 checks that prove the claims of move 9: each a few lines with a `check(boolean,String)` helper; prints `ALL PASS` at the end or exits non-zero). Rules for the Java:
   - Javadoc on EVERY class, interface, enum and method: one or two lines saying what it is for and what it guarantees (he skims the green comments first).
   - The critical step commits nothing before the irreversible external action succeeds (pay before commit; reserve then confirm; append then index): a failed action leaves state exactly as it was and the caller can retry.
   - One lock per aggregate root (`ReentrantLock`), the critical section holds only lookups and field writes; observers/listeners are called AFTER unlock with try/catch so a broken listener cannot break the flow; time is injected through an interface (`interface Clock { long nowMs(); }`) so tests can set it.
   - Rules behind one-method interfaces handed in through `configure(...)`; the aggregate never builds them.
   - O(1) shapes: per-size deques, maps by id; `EnumMap`; a Fit/allowed table instead of if-chains; `AtomicInteger` ids.
   - JDK 21, no external libraries, `javac Main.java Extensions.java FailureTests.java && java FailureTests` must print ALL PASS (the engine runs exactly this).
   `code_intro`: two sentences: read the green comments first for the shape; each copy button copies that file; the javac line.
5. **Follow-ups and practice** (`implement_card_html`, `followups`): the implement card (`<div class="card"><div class="ch"><h3>0 &middot; Implement the system</h3><button class="timer" data-min="60">start 60:00</button></div><div class="cb"><div class="prompt">the prompt again</div>the typing order: enums, models, the two interfaces with one implementation each, the aggregate with its lock and the critical order, the callers, a main with the race</div></div>`) then 10-13 follow-ups `(question, kind, minutes, answer_html, code)` where kind is one of `functional | non-functional | twist | design`, minutes 3-10, the answer is 3-6 plain sentences saying what the reference code DOES (not why it is elegant), and the code is the exact snippet from Extensions.java or Main.java (slice it with `sect(src,"class X","class Y")` so it stays in sync). Always include: the surge/rule-change twist (Decorator), the race test, "does one lock scale", the failure-at-the-critical-step, the O(1) query, two real twists of this system (the ones interviewers actually ask), persistence/repository, where time comes from + how to test it, which pattern is where and why, which SOLID letter is where, enum-vs-subclass/Factory.

## Quality gates before you report
- `python3 specs/<slug>.py` prints `guard: compiles; FailureTests ALL PASS` (the engine enforces it). Also run `java Main` and `java ExtDemo` in a temp dir: both must run without an exception.
- Screenshot each of the five pages: `sed "s/let cur=parseInt(localStorage.getItem('<slug>.step')||'1',10);/let cur=N;/" <slug>-workbench.html > /tmp/x.html` then headless Chrome (`"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu --hide-scrollbars --window-size=1700,6000 --virtual-time-budget=5000 --screenshot=/tmp/xN.png file:///tmp/x.html`) and LOOK at them with the Read tool: no label spilling out of a box, no overlapping arrows, no empty bands, every picture's text readable.
- Every fact in the derivation matches the code (the order at the critical step, the names of classes and methods, the numbers).
- Plain English test: no sentence a strong SDE-2 would have to read twice.
